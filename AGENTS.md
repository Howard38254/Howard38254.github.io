# Portfolio editing workflow

The user wants exact, scoped changes and a Markdown editing source synchronized with the website.

- Read WEBSITE-CONTENT.md before editing website content, structure, styling, or behavior.
- Treat it as the main editable content and design specification. Apply explicitly edited fields and ADD/CHANGE/HIDE/REMOVE instructions; preserve unrelated content and design.
- KEEP means keep the section; user edits to its fields still express requested changes.
- Do not invent facts or publish blank template/instruction text as website copy.
- A saved Markdown edit does not itself publish the website. Apply edits when the user requests application; publish within the user's authorized scope.
- For changes requested in chat, update WEBSITE-CONTENT.md in the same task to reflect the resulting website.
- After applying changes, reconcile section order, menu links, project gallery and detail content, assets, and destinations. Update the synchronization date, pending work, and publication state honestly.
- Mark applied requests as completed in the synchronization record and restore section statuses to KEEP. Retain explicit removals in a brief change record.
- If the document and website differ, preserve the user's edited document and report/apply its pending changes when requested; do not overwrite the document with an export of the old website.
- If both the local and GitHub copies changed, inspect both and preserve the user's edits. Ask only when there is a real conflicting instruction.
- Keep supporting docs consistent; WEBSITE-CONTENT.md takes precedence over older concept/template guides.
- Current website is buildless: index.html, site.css, site.js. The old Refined Builder template is archived; never rebuild the current site from it.
